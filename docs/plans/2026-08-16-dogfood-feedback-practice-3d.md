# Dogfood 피드백: practice-3d 런에서 나온 개선 고민 3가지

작성: 2026-08-16, practice-3d(비눗방울 포트폴리오) 런 도중.
상태: **결정 완료 (2026-08-16)** — 셋 다 결정·스킬 반영됨 (0.3.4).
결정 요약은 문서 말미 "결정 기록" 섹션.

## 배경 (증거 위치)

- 도그푸드 대상: `~/code/practice-3d` — talpi 0.3.x로 spec→plan→build 진행,
  이 문서 작성 시점에 phase 3/3 빌드 중.
- 비교군: 같은 제품을 superpowers 플러그인으로 ~15분 만에 만든 버전이
  `practice-3d`의 `superpowers-version` 브랜치에 있음.
- 읽기 전용 비교 리뷰 결론: talpi 산출물이 명확히 우위 (테스트 16개,
  WebGL 폴백, 더블팝/커서꼬임/뷰포트 하드코딩 버그 부재, 요구사항 드리프트
  사전 차단). 단, 아래 3가지 약점도 드러남.

## 고민 1 — 위임 구역 내부의 모듈화 압력 부재

**증상**: `practice-3d/src/scene/BubbleField.tsx`가 772줄 (셰이더 + 파티클
+ 모션 + 호버 + 컴포넌트 4개가 한 파일). 경계 수준 모듈화는 훌륭했음
(registry / 파생 모듈 / 라우팅 / webgl 프로브 / 테마가 전부 분리).

**진단**: conventions baseline의 추출 규칙이 "로직이 **두 번** 나오면
공유 레이어로"라서 **재사용 압력만 있고 크기·응집 압력이 없다**.
Delegated 구역 내부는 어떤 형태 규칙도 안 받는 사각지대.
(참고: 프리랜딩 리뷰에서 이 파일이 "cohesive하지만 크다"로 언급됐으나
컨벤션 위반이 아니라 통과됨.)

**선택지 (논의용, 결정 아님)**:
- (a) baseline 4번 규칙 추가: "파일이 N줄(예: 300)을 넘으면 컴포넌트/관심사
  단위 분리를 검토하고, 안 나누면 이유를 conventions.md에 한 줄" —
  하드 리밋이 아니라 검토 트리거.
- (b) verifier 프롬프트에 크기/응집 신호를 [NOTE] 수준으로 넣기 (비차단).
- (c) 아무것도 안 함 — 위임 구역은 위임 구역답게. 단일 파일도 응집이면 OK.
- 긴장: talpi 철학은 "내부는 침묵"인데 (a)(b)는 내부에 형태 규칙을 넣는 것.
  단, conventions.md는 원래 내부 형태 규칙의 집이므로 모순은 아닐 수도.

## 고민 2 — 화면단(비주얼) 검증이 눈 검수로만 남는 문제

**증상**: practice-3d 테스트 16개는 전부 경계 계약(등록부/라우팅/폴백).
제일 복잡한 코드(호버 정지, 터짐 파티클, 셰이더)는 검증 스토리가 "사람이
본다"뿐. 이번 스펙도 Simplicity Zones에서 "비주얼은 눈으로"를 명시해서
규칙상으로는 정상 동작.

**현실 제약 (오늘 실측)**: 헤드리스 Chromium(SwiftShader)에서 WebGL
컨텍스트 생성 실패 — 3D 씬은 헤드리스 스크린샷이 안 될 수 있다.
반면 DOM 페이지(폴백/작품 페이지)는 헤드리스 스크린샷 잘 됨.

**선택지**:
- (a) verifier에 스크린샷 스텝(옵션): DOM 표면은 헤드리스로,
  WebGL 표면은 실브라우저 자동화(가능하면)로 캡처 → 결과를 [VISUAL]
  리포트(비차단)로 사람에게 첨부. "눈 검수"를 없애는 게 아니라
  **눈에 보일 재료를 자동으로 배달**하는 방향.
- (b) phase 보고 시점에 "사람 검수 체크리스트"를 명시 생성 (스모크
  시나리오에서 파생) — 지금은 검수 항목이 암묵적.
- (c) 씬 로직을 렌더와 분리해 순수 함수로 뽑아 단위 테스트 (예: 모션
  수식, 터짐 상태기계). 비주얼 자체가 아니라 비주얼의 *수학*을 테스트.
  practice-3d의 dampTo/euclideanMod/mulberry32가 이미 이 모양 — 규칙화 여지.
- 참고: 이전 talpi 수정 세션에서도 같은 문제가 나왔었음 (사용자 기억).

## 고민 3 — 프로세스 무게: light/heavy 이분법 vs 비례 원칙

**증상**: superpowers ~15분 vs talpi 몇 시간. 시간이 간 곳: 스펙 패널
3명 × 최대 3라운드, 스텝마다 신선한 구현 에이전트, phase별 verifier,
journal/handoff/conventions 유지. 이 프로젝트(경계 4개, 개인 연습장)
기준으로 패널 3×3은 체감 과잉.

**핵심 질문**: light/heavy 모드를 나눌 것인가, 아니면 talpi의 자기 철학
"두께는 경계 표면에 비례"를 **프로세스 노브에도 적용**해 연속적으로
스케일할 것인가.

**선택지**:
- (a) 모드 이분법: `talpi --light` (패널 1명 1라운드, verifier 통합,
  journal 간소). 단순하지만 talpi가 비판하던 "프로젝트 크기 기준" 사고로
  회귀할 위험.
- (b) 비례 자동 유도: 스펙 완성 시점에 노브를 계산 — 예: 패널 리뷰어 수
  = f(계약 수, 외부 터치포인트 수, 시크릿/개인정보 유무), 재실행 캡,
  스텝 에이전트 신선도(매 스텝 vs 매 phase), 저널 밀도. 스펙이 얇으면
  프로세스도 저절로 얇아짐. 철학과 일관되지만 튜닝 어려움.
- (c) 혼합: 기본은 (b), 사람이 스펙 승인 시점에 노브를 한 번 보고
  오버라이드 (마지막 게이트에 "이 무게로 갈까요?" 한 줄 추가).
- 데이터 포인트: 이번 런에서 패널이 실제로 잡은 것 — 1라운드에서 진짜
  BLOCKING 5건 (전부 유효), 2라운드에서 문구 모순 2건 (유효하지만 잔잔),
  3라운드는 사실상 수확 없음. "1라운드 무제한 + 이후 축소"는 이미 잘
  설계됐고, 라운드 수보다 **리뷰어 수**가 조정 여지일 수 있음.

## 다음 세션 진행 제안

1. 고민 1~3을 순서대로, 각각 "선택지 채택/기각/새 안"을 결정.
2. 결정된 것을 talpi 스킬 파일(talpiplan의 conventions 초안 로직,
   talpirun의 verifier 프롬프트, talpispec의 패널 디스패치)에 반영.
3. practice-3d 런이 끝났다면 그 결과(phase 3 verifier 리포트, 최종
   fresh-eyes 리뷰)도 증거로 추가 활용.

## 결정 기록 (2026-08-16, 0.3.4 반영)

### 고민 1 → (a) 채택

conventions baseline에 4번 규칙 추가: 파일이 ~300줄을 넘으면 관심사
단위 분리를 *검토*하고, 안 나누면 이유를 Layout & Naming에 한 줄 기록
— 기록된 예외는 finding이 아님 (하드 리밋 아니라 검토 트리거).
근거: BubbleField.tsx가 882줄까지 자란 이유는 각 관심사가 한 번씩만
등장해 "두 번이면 추출" 규칙이 영원히 발화하지 않아서 — 재사용 압력만
있고 크기 압력이 없었음. conventions.md는 원래 내부 형태 규칙의 집
(Layout & Naming 섹션)이라 "내부는 침묵" 철학과 모순 없음. (b)는
별도 반영 불필요 — verifier가 기존 "conventions 위반 체크" 경로로
자동 커버.

### 고민 2 → (b)만 채택, (c) 보류, (a) 기각

talpirun에 명문화: phase가 눈 검수 존 표면을 만들거나 바꾸면 phase
보고 전에 검수 항목을 `.talpi/manual-check.md`에 누적 (코드 안 읽고
걸을 수 있는 수준), 최종 인수 때 체크리스트를 함께 건넴 — 사람이
체크리스트를 걷는 것이 눈 검수 존의 검증 스토리. practice-3d 런이
즉흥적으로 만든 manual-check.md의 비준.
- **(a) 스크린샷 기각**: 헤드리스 WebGL 실측 실패로 환경 의존적
  기계장치가 필요해지고, 0.3.3 오버헤드 컷 방향과 역행.
- **(c) 순수 로직 분리+단위 테스트 보류**: 근거 버그(더블팝/커서
  꼬임)는 superpowers 비교군에서 나온 것이지 talpi 산출물이 아님 —
  안 터진 총에 규칙 달기. 게다가 고민 1의 분리 트리거가 순수 헬퍼
  추출 압력을 이미 만들어 절반은 공짜로 얻음. **talpi 산출물에서 이
  부류 버그가 실제로 나오면 그 증거로 재론.**

### 고민 3 → 최소 비례 노브 (신규 안, (a)(b)(c) 모두 원형 그대로는 기각)

스케일 안 하는 상수가 패널 디스패치 하나뿐이라는 진단에서 출발 —
re-run은 이미 스코프+캡으로 수렴 설계돼 있고(데이터: 1라운드 5건
유효 → 3라운드 0건), verifier는 phase 수에 비례, 스텝 오버헤드는
0.3.3에서 컷. talpispec에 반영:
- 초안 스펙 표면이 얇으면(계약 소수 — 신호지 컷오프 아님 — +
  스키마/인증/데이터 소유권류 렛저 후보 없음 + 시크릿/PII/멀티유저
  없음) 세 렌즈를 1인 리뷰어가 한 컨텍스트에서 수행, re-run 캡 1.
  렌즈를 버리는 게 아니라 디스패치를 합치는 것.
- **thin 분류 폐기는 통합 규칙**: 파인딩이 분류를 반박하든 사람이
  승인 전 풀 패널을 요구하든, thick 경로 시작점으로 재진입 — 언스코프드
  3인 1회(adjudicated 항목은 프롬프트가 아니라 수집 단계에서 렛저
  기록으로 유지 — 목록을 리뷰어에 주면 스코핑이 다시 스며듦) 후 정상
  스코프 재실행 캡 2. 폐기는 한 번만 — 이후는 thick 경로의 수렴성
  상속.
- 승인 제시 때 패널 판형을 한 줄로 명명 — 사람의 오버라이드 지점은
  디스패치 전 공지가 아니라 여기 (thin 런 결과를 보고 판단하는 쪽이
  더 정보 있는 오버라이드).
- 나머지 노브(스텝 신선도, journal 밀도)는 이번에 안 건드림 —
  0.3.3 효과를 다음 도그푸드에서 관측 후 재론.
